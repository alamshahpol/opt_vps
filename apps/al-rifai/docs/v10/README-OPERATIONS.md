## Core connection

No production Core values were configured or verified in this build. Required hosted server configuration:

- `FAZLE_CORE_URL`: trusted reachable HTTPS origin, without credentials, path, query or fragment.
- `FAZLE_CORE_READ_KEY`: read-scoped credential accepted by the Core vessel-read route. Never substitute an administrator/internal superuser key.

Set `FAZLE_CORE_VESSEL_READ_VERIFIED=true` only after verifying the canonical endpoint, its schema, absence of GET side effects, and read-scoped permission against the actual deployed Core. Without that verification flag, reads fail closed. The only upstream data operation is GET `/api/integration/v1/programs`, paged with 200 rows and a maximum of ten pages. Requests have a 25-second total deadline, redirects are denied, JSON responses are bounded to 3 MB per page, and a field allowlist strips payroll, client, cargo/capacity and internal fields. Browser responses never include the key or upstream URL. Automatic refresh runs every 60 seconds only while the live view is visible; manual Refresh is always available.

The canonical gateway was proposed in the previous integration contract and is not established on the current VPS. It must return `{items,total,page,page_size}` with stable canonical program IDs, explicit program statuses, and the program fields from `wbom_escort_programs`; existing snake-case and register camel-case names are accepted. Missing values remain unknown. The Site does not substitute derived roster or payroll data for the canonical register. Credential acceptance by the earlier FPE-only routes does not establish permission for this gateway. No VPS implementation or migration has been performed.

Live pages are not a transactional snapshot. Overlapping IDs, changing totals and incomplete pages fail closed. More than 2,000 source rows produce a partial-data label; summaries and answers cover only loaded records. An error retains the previous successful results with a stale label. Core data is never persisted in this Site or merged into the archive.

## Register assistant

A working conservative structured-query mode supports counts, summaries, matching records, destination/status groupings and missing key fields. Unsupported or ambiguous conditions produce an uncertainty response. The assistant opens in a small nonmodal popup. Pointer capture supports dragging its header in both directions; arrow keys move a focused header, positions stay within the viewport, and resizing reclamps the window. Escape/Close restores focus to its launcher. Historical accounts queries are deterministic, include transaction source links and exact applied cash filters, and refuse unknown conditions/ambiguous employee names. Workflow questions return explicitly labeled guidance without claiming record facts or changes. Every answer names its source and includes supporting record links. Source switches clear local conversation state.

Optional model query interpretation is implemented with OpenAI structured output. Hosted runtime configuration is `OPENAI_API_KEY` (secret) and `REGISTER_AI_MODEL` (a model supporting strict JSON schema; `OPENAI_MODEL` is accepted as an alias). Provision any key through the OpenAI Developers plugin’s canonical key skill; no key was minted or configured here because the plugin is unavailable. The model receives only the question, applied filters and bounded catalogs of source names/statuses, not phone numbers, notes, raw messages or full records. It has no tools. Server-side schema validation turns its plan into an allowlisted read query, and deterministic code computes the final answer from retrieved data. The model never authors record facts or final prose. Refusals, malformed plans and errors fall back to visibly labeled structured mode.
